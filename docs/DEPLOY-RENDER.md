# Deploy — Render

ResearchTrics deploys to **Render** as two long-running services plus managed
Redis, defined as Infrastructure-as-Code in [`render.yaml`](../render.yaml). Neon
Postgres is external.

## Stack
| Service | Render type | Purpose |
|---|---|---|
| `researchtrics-web` | Web Service | Next.js app (`next start`), API, middleware |
| `researchtrics-worker` | Background Worker | BullMQ jobs (health, OJS sync, discovery) |
| `researchtrics-redis` | Key Value | Redis for BullMQ (no Upstash needed) |
| Neon | external | Postgres (`DATABASE_URL` / `DIRECT_URL`) |

Object storage is **not** on Render — pair with Cloudflare R2 or AWS S3 and set
the `OBJECT_STORAGE_*` vars (the storage layer is S3-compatible).

## One-time deploy
1. Push `render.yaml` to the repo (branch `build/researchtrics-mvp`).
2. Render → **New → Blueprint** → select this repo. Render reads `render.yaml`
   and proposes the three services + the `researchtrics-secrets` env group.
3. Fill the `sync: false` secrets in the env group:
   - `DATABASE_URL` / `DIRECT_URL` — the Neon pooled + direct URLs.
   - `TOKEN_ENCRYPTION_KEY` — `openssl rand -base64 32` (must decode to 32 bytes).
   - `OBJECT_STORAGE_*` — your R2/S3 bucket + keys.
   - `NEXT_PUBLIC_APP_URL` (on the web service) — the live URL; it is **baked at
     build time**, so set it before the first build.
   - `SESSION_SECRET` is generated by Render automatically.
4. Apply. Render builds both services; the web service's `preDeployCommand` runs
   `prisma migrate deploy` against Neon before going live.

## Notes
- **Node** is pinned to 22 via `NODE_VERSION`; pnpm comes from `corepack`
  (`packageManager: pnpm@9.15.9`).
- **Health check**: the web service uses `/api/v1/health` (200 when the DB is
  reachable, 503 otherwise — so a bad DB connection blocks a broken deploy).
- **Free tier**: the web service can run on `free` for staging (idle spin-down /
  cold starts). Background Workers and `preDeployCommand` require a paid instance
  — on `free`, drop `preDeployCommand` and run `prisma migrate deploy` manually.
- **Migrations already applied** to the current Neon DB, so the first
  `preDeployCommand` is a no-op; it exists for future schema changes.
